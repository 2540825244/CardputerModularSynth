# v1.3 plan: optimized, sampling-first (2026-10-29)

Spec: `docs/superpowers/specs/2026-10-27-cardputer-modular-design.md` (§14.1 is the v1.2 state).
Backlog this plan absorbs: `docs/todo.md`.

**Owner goals (2026-10-29):** "highly optimized and feature rich and full of presets that actually
work, enough to let me sample into the PO-33"; a module bypass/disable "for overhead protection";
"demand driven module activation" for a utility module that plays every sound of a drum set in one
go (some stacked, the PO-33 is mono per sample) and "mimics a sequencer to trigger the sound sources".

## Global constraints
- Hardware: ESP32-S3FN8, no PSRAM, 240 MHz, 16 KB shared I-cache, flash runs DIO (Launcher's
  bootloader). Audio on core 1 (8 KB stack), UI on core 0.
- **The app image must stay <= 1,048,576 bytes** (the Launcher's `modsyn` slot). Report the size
  after every build. Target <= 960 KB after Task 2 so later tasks have room.
- **Device access** (owner: "do not go over dangerous territory"): port `/dev/cu.usbmodem1101`. Only
  ever write the `modsyn` slot: `esptool.py --chip esp32s3 --port /dev/cu.usbmodem1101 -b 921600
  --after hard_reset write_flash -z 0x650000 <bin>`. Never write or erase anything else (bootloader,
  partition table, otadata, nvs, other app slots), never `erase_flash`. Helper scripts:
  `tools/dev/flash_slot.sh <bin> <secs> <out>` (writes the slot, resets, captures serial) and
  `tools/dev/listen.py <port> <secs>`. Backup of the whole flash: `dist/flash-backup-2026-10-29.bin`.
- CPU numbers come from the device: `pio run -e bench` (src/bench/bench_main.cpp) flashed into the
  slot prints cycles/sample per type with the UI at 30 fps. Budget: 4000 of 5000 cycles/sample.
  Every perf task reports before/after from the device, and updates the type's `cpuCycles`.
- Sound must not change unless a task says so: perf rewrites get a native test comparing the old
  and new output (see `test_ladder_matches_daisysp`).
- Tests: `~/.platformio/penv/bin/pio test -e native` all green; device build `pio run -e cardputer`.
- DaisySP (MIT core) and Plaits (MIT) are vendored: editing them is fine; mark edits
  `// modsynth:` and list them in the library's UPSTREAM/README note.
- Patch file format: additive only (old files load; new keys optional).
- At the end of every task: flash the normal firmware back into the slot so the owner's device works.

## Task 1: SD card does not mount
Boot prints `sd_diskio.cpp:806 sdcard_mount(): f_mount failed: (3) The physical drive cannot work`;
the card is in and the Launcher reads it. Find why (pins, SPI host/bus sharing with the display,
clock, init order, card type) on the device, fix it, and show `SD ok` with the card size on serial,
plus a save/load round trip (file view) working. See `src/hw/sd_storage.*`, `docs/hardware-spec.md`.

## Task 2: flash budget
Image is 995 KB of 1024. Find what takes flash (map file / `nm --size-sort`): M5GFX/M5Unified
drivers and fonts not used, Plaits/DaisySP code never referenced, ArduinoJson, presets, -O2 on
non-DSP code. Cut to <= 960 KB without slowing the audio path (UI and libraries may go -Os; DSP
stays -O2). Report the top 20 contributors before/after.

## Task 3: DaisySP control-rate coefficients
Measured (cyc/sample, UI 30 fps): SNR 10738, MDL 9694, HAT 6870, RES 6301, KCK 3297, STR 2829,
AWH 2664, VOS 2139, ZOS 1580, SSW 1459, FMO 976, FOR 786, VSO 763, QNT 741, LAD 801.
DaisySP drums and physical models recompute coefficients every sample (the snare: 2 powf and six
SVF SetFreq/SetRes with sinf/powf per sample). Recompute only when an input changes (dirty flags)
or once per 32-sample block, keep per-sample what must be (envelopes, audio). Also replace float
divisions in hot loops with `recipPos` (core/dsp_util.h) or precomputed reciprocals, and libm calls
with the fast helpers. Goal: every source type <= 1500 cyc/sample, drums <= 1000. Native tests that
the output with static params matches the old code (tolerance stated per module).

## Task 4: GRD, engine and remaining hot spots
- **GRD first** (the owner's headline complaint: "a single grind still overloads the cpu"; the
  owner's autosave runs at ~127 % with one GRD). Per engine on the device (bench and the real
  firmware), find and fix the hot spots: the 12-sample Plaits chunking vs the 32-sample block, the
  per-sample envelope/LFO/cutoff work in grd.cpp, Plaits' own per-sample divisions and libm calls
  (Plaits is vendored, MIT; mark edits `// modsynth:`), denormals. Goal: GRD's worst engine with the
  ladder on <= 2500 cyc/sample in the real firmware, so GRD + a small patch fits the 4000 budget.
- **Tilt polling** costs the audio ~600 cyc/sample (the IMU I2C read on every UI loop, core 0):
  poll only while a TILT module exists or a tilt gesture is active, and at <= 50 Hz.
- Engine per output sample: sanitize + peak cost ~40 cyc (float compares). Use integer compares on
  the float bits (|x| <= 50 fast path, NaN/Inf -> 0); peak from the same pass.
- Re-bench all types; take the top 10 left and fix the cheap wins (divisions, out-of-line calls,
  per-sample coefficient updates). Report the table.
- If code-layout noise (±20-30 % for identical code) still decides whether GRD fits, move the
  hottest per-sample code into IRAM here (Task 9's item), staying within ~32 KB of heap.

## Task 5: module bypass
- Per-module `bypass` flag in the patch (saved as `"bypass":true`, undoable).
- Bypassed: not processed (zero CPU, not counted by the guard). Effects/processors (types with an
  audio input 0 and output 0) pass input 0 to output 0; everything else outputs 0.
- UI: a key gesture on a selected module in the patch view toggles it (pick a free one that fits the
  side-key scheme in the spec; show it in the side icons and help); the tile draws dim with a slash.
  Un-bypassing goes through `canAddLive` (fn+gesture forces, like placing).
- Tests: engine skips bypassed nodes, passthrough, save/load, undo.

## Task 6: KIT module (demand-driven drum-pack sampler)
A utility/sequencer module for recording a whole kit into the PO-33 in one take.
- Outputs: 8 trigger outputs (T1..T8). Steps: up to 16; each step is a bitmask of outputs fired
  together (stacked hits). Params: step count, gap (ms between steps, ~150-1500), accent, mode
  (one-shot / loop). Inputs: RUN (gate/trigger starts a pass), CLK (optional external step clock).
  Pages: a step grid (cells = steps x outputs) like SEQ/TRG.
- Starting a pass: RUN input, or enter on the KIT view (and the PLAY side key).
- **Demand-driven activation:** the engine finds, for each KIT output, the modules fed only from it
  (its exclusive downstream subgraph: a module whose every connected input traces back to that
  output alone). Those modules are processed only while their output's step is sounding: from the
  trigger until their exclusive outputs stay below -60 dB for 50 ms, or the gap ends. Shared
  modules (mixers, OUT, FX after the mix) always run. Idle grouped modules output 0 and cost 0.
- CPU guard: a patch's cost = always-on modules + the most expensive set of groups that a single
  step can fire at once (not the sum of all groups).
- Tests: grouping (exclusive vs shared), activation window, guard arithmetic, a 3-drum kit (KCK +
  SNR + HAT, each heavy) runs under budget on the device.

## Task 7: presets that work, for the PO-33
- A preset library (~30+) built for sampling: drum kits via KIT (808-ish, 909-ish, lo-fi, metallic,
  Plaits drums), basses, leads, plucks, pads/drones, chords, FX/risers/noise, GRD voices.
- Every preset makes sound on its own (KIT, SEQ or a clock: no keyboard needed) and has a KEYS
  module where it makes sense for playing.
- Levels: normalised for the PO-33 line in (peak around -3 dBFS at OUT, no clipping).
- Device check: the bench loads every preset, runs 3 s, prints CPU % (must be < 80 %), peak, RMS,
  and flags silence or clipping. All presets pass on the device.
- Presets are authored in `tools/presets.py` / `tools/presets_more.py` (run `python3 tools/presets.py`).
